# Kata Containers คืออะไร ทำงานยังไง และช่วยเรื่องความปลอดภัยได้แค่ไหน

ส่วนนี้ film เขียนสำหรับรายงานกลุ่ม (ข้อ 3.1) ตัวเลขที่ยกมาเป็นผลที่วัดได้จริงจาก cluster ของเราตอนทำ B2

## 1. Kata Containers คืออะไร

เวลาเรารัน container ใน Kubernetes แบบปกติ ตัวที่ทำงานอยู่เบื้องหลังคือ runc ซึ่งจริง ๆ แล้วไม่ได้สร้างเครื่องใหม่อะไรขึ้นมาเลย มันแค่ใช้ namespace กับ cgroup ของเคอร์เนล Linux มากั้นไว้ ให้ process แต่ละกลุ่มมองไม่เห็นกัน และจำกัดว่าใช้ CPU กับ RAM ได้เท่าไร วิธีนี้เบาและเร็วมาก แต่มีจุดอ่อนใหญ่อยู่ข้อหนึ่ง คือทุก container บนเครื่องใช้เคอร์เนลตัวเดียวกับเครื่อง ถ้าวันหนึ่งเคอร์เนลมีช่องโหว่ แล้วมี container ตัวไหนเจาะได้ ก็อาจหลุดออกมาคุมทั้งเครื่องได้

Kata Containers เกิดมาเพื่อแก้ตรงนี้ แนวคิดของมันคือข้างนอกหน้าตาเหมือน container ทุกอย่าง แต่ข้างในเป็น VM ทุก pod ที่รันด้วย Kata จะได้ VM ขนาดเล็ก (micro-VM) ของตัวเอง มีเคอร์เนลของตัวเองแยกจากเครื่อง เท่ากับได้การแยกขาดระดับ VM มา ในขณะที่คนใช้ยังสั่งผ่าน `kubectl` ได้เหมือนเดิม

Kata มาจากการรวมกันของสองโปรเจกต์ คือ Intel Clear Containers กับ Hyper runV ช่วงปลายปี 2017 ตอนนี้เป็นโปรเจกต์โอเพนซอร์สที่อยู่ภายใต้ OpenInfra Foundation

ถ้าเทียบกันตรง ๆ จะได้ประมาณนี้

| | runc (container ปกติ) | Kata Containers |
|---|---|---|
| กั้นกันด้วยอะไร | namespace กับ cgroup ของเคอร์เนลเครื่อง | VM ที่มีเคอร์เนลของตัวเอง |
| เคอร์เนล | ใช้ร่วมกับเครื่อง | แยกกันคนละตัวต่อ pod |
| เริ่มทำงาน | เร็วมาก | ช้ากว่า เพราะต้องบูต VM ก่อน |
| RAM ที่เสียเพิ่ม | แทบไม่มี | ทุก pod มี overhead ของ VM |
| ใช้ใน Kubernetes | เป็นค่า default อยู่แล้ว | เพิ่ม `runtimeClassName: kata` บรรทัดเดียว |

## 2. สถาปัตยกรรม

### 2.1 ภาพรวม

ลองไล่ตามเส้นทางของคำสั่งตั้งแต่เราพิมพ์ `kubectl` ไปจนถึงตอนที่ pod รันจริง

```
kubectl ──► kata-master (K3s API)
                │  สั่งให้สร้าง pod
                ▼
           kata-worker-1
           ├─ kubelet
           ├─ containerd
           │    ├─ runc ─────────────► container (ใช้เคอร์เนลเครื่อง)
           │    └─ Kata shim (runtime-rs)
           │          │ สั่งสร้าง VM
           │          ▼
           │       QEMU  ═══ micro-VM ═══════════════════╗
           │                ║ เคอร์เนล VM (6.18.35)      ║
           │                ║ kata-agent                 ║
           │                ║   └─ container (nginx)     ║
           │                ╚════════════════════════════╝
           └─ เคอร์เนลเครื่อง (7.0.0-1014-aws) + KVM
```

คำสั่งของเราวิ่งไปที่ kata-master ก่อน แล้ว master ส่งต่อให้ worker สร้าง pod ถึงตรงนี้ทั้ง runc และ Kata ยังเหมือนกัน ทางเริ่มแยกตอนที่ containerd บน worker ต้องเลือกว่าจะใช้ runtime ตัวไหน ถ้าเป็น runc ก็สร้าง container บนเคอร์เนลเครื่องไปเลย ถ้าเป็น Kata จะต้องสร้าง VM ขึ้นมาก่อน แล้วค่อยไปสร้าง container ข้างในนั้น

### 2.2 แต่ละส่วนทำหน้าที่อะไร

**RuntimeClass** เป็นวิธีที่ Kubernetes ใช้เลือก runtime ทีละ pod ใน cluster ของเรามี RuntimeClass ชื่อ `kata` อยู่ (ดูได้ใน `infra/k8s/runtimeclass.yaml`) pod ไหนใส่ `runtimeClassName: kata` ไว้ containerd ก็จะส่ง pod นั้นไปให้ Kata แทน runc

**Kata shim** (ชื่อเต็มคือ containerd-shim-kata-v2) เป็นตัวกลางที่ containerd คุยด้วย หน้าที่ของมันคือสร้าง VM เตรียมเครือข่ายกับพื้นที่เก็บไฟล์ แล้วส่งคำสั่งต่อเข้าไปใน VM เราใช้ Kata 4.1.0 แบบ runtime-rs ซึ่งเป็น shim ที่เขียนด้วยภาษา Rust

**Hypervisor** คือตัวที่สร้าง VM จริง ๆ Kata ใช้ได้หลายตัว เช่น QEMU, Cloud Hypervisor หรือ Firecracker ของเราใช้ QEMU โดยมี KVM ในเคอร์เนลเครื่องช่วยให้ VM รันได้เร็วเกือบเท่าเครื่องจริง

**Guest kernel** คือเคอร์เนลที่บูตอยู่ใน VM ถูกตัดส่วนที่ไม่จำเป็นออกให้เล็กและบูตเร็ว ของเราเป็นเวอร์ชัน `6.18.35`

**Guest image กับ kata-agent** คือระบบไฟล์ขนาดเล็กที่ VM บูตขึ้นมา ข้างในมีโปรแกรมชื่อ kata-agent คอยรับคำสั่งจาก shim ผ่านช่องทางพิเศษระหว่างเครื่องกับ VM ที่เรียกว่า vsock แล้วเป็นคนสร้าง container ตัวจริงขึ้นมาข้างใน VM

ส่วนไฟล์ของ container จะถูกส่งเข้าไปใน VM ผ่านอุปกรณ์เสมือนแบบ virtio (เช่น virtio-fs) VM ไม่ได้แตะดิสก์ของเครื่องตรง ๆ

### 2.3 ของจริงใน cluster ของเรา

| เรื่อง | ค่าที่เจอ | ดูจากไหน |
|---|---|---|
| Kubernetes | K3s v1.37.2 | `infra/REAME.md` |
| Kata | 4.1.0 (runtime-rs + QEMU) | `infra/REAME.md` |
| เครื่อง worker | EC2 `m8i.large` (2 vCPU, RAM ราว 8 GB) เปิด nested virtualization | `infra/REAME.md` และผลทดสอบ B2 |
| เคอร์เนลใน VM | `6.18.35` | `uname -r` ใน pod Kata |
| CPU ของ VM | 1 | `nproc` ใน pod Kata |
| RAM ที่ pod มองเห็น | 192 MB | `free -m` ใน pod Kata |
| ขนาด VM เมื่อมองจาก worker | 288 MB | james ดูด้วย `ps` บน worker |
| overhead ที่จองไว้ต่อ pod | 100m CPU / 160Mi RAM | `runtimeclass.yaml` |
| พารามิเตอร์ตอนบูต | `root=/dev/pmem0p1`, `systemd.unit=kata-containers.target`, `console=hvc0` | `dmesg` ใน pod Kata |

มีอยู่สามเรื่องที่เราสังเกตจากตารางนี้

เรื่องแรก worker ของเราเองก็เป็น VM ของ AWS อยู่แล้ว การจะรัน VM ของ Kata ซ้อนเข้าไปอีกชั้นเลยต้องเปิด nested virtualization ไว้ ถ้าเป็นเครื่องจริงแบบ bare metal จะไม่ต้องทำขั้นนี้

เรื่องที่สอง james พบว่า Kata 4.x ตั้งขนาด VM ตาม RAM ที่ pod ขอ container ใน cluster เราได้เพดาน RAM default ที่ 256Mi แล้ว VM ที่ออกมามีขนาด 288 MB แต่พอเข้าไปดูจากใน pod กลับเห็นแค่ 192 MB เราคิดว่าส่วนที่หายไปเป็นของที่เคอร์เนลใน VM กันไว้ใช้เอง แต่ข้อนี้ยังเป็นแค่การตีความของเรา ยังไม่ได้เช็กกับเอกสารของ Kata

เรื่องที่สาม RuntimeClass ของเราตั้ง `overhead` ไว้ด้วย เพื่อให้ Kubernetes นับ RAM กับ CPU ที่ VM กินเพิ่มเข้าไปในโควตาของแต่ละคน ถ้าไม่ตั้งไว้ โควตาจะดูเหมือนยังเหลืออยู่ ทั้งที่เครื่องจริงถูกใช้ไปมากกว่านั้น

## 3. ความปลอดภัย

### 3.1 container ปกติมีปัญหาอะไร

สิ่งที่ Kata อยากป้องกันเป็นหลักคือ container escape หรือการที่คนที่อยู่ใน container หาทางหลุดออกมาถึงเครื่อง host ได้ container แบบ runc คุยกับเคอร์เนลเครื่องโดยตรงผ่าน system call พอเคอร์เนลมีบั๊ก container ก็ใช้บั๊กนั้นได้ทันที ที่ผ่านมามีช่องโหว่เคอร์เนลหลายตัวที่ถูกเอามาใช้หลุดจาก container แล้ว เช่น Dirty COW (CVE-2016-5195) กับ Dirty Pipe (CVE-2022-0847)

ลองนึกถึง cluster ของเราเอง มี 5 คน 5 namespace แต่ worker มีเครื่องเดียว ถ้า pod ของใครคนหนึ่งหลุดออกมาได้ ก็แปลว่าเข้าถึง pod ของทุกคนบนเครื่องนั้นได้ด้วย namespace ของ Kubernetes แค่ช่วยแยกว่าใครสั่งอะไรได้บ้าง แต่ไม่ได้แยกเคอร์เนลให้

### 3.2 Kata ช่วยได้ยังไง

Kata ไม่ได้ทำให้เคอร์เนลหายจากบั๊ก สิ่งที่มันทำคือเพิ่มชั้นกั้นขึ้นมาอีกหนึ่งชั้น

```
runc:  [nginx] ── เคอร์เนล worker (ใช้ร่วมกัน) ── เครื่อง
kata:  [nginx] ── เคอร์เนล VM ── qemu ── เคอร์เนล worker ── เครื่อง
                  └─ ชั้นกั้นที่เพิ่มขึ้น ─┘
```

สมมติว่าคนใน pod Kata ใช้ช่องโหว่เคอร์เนลได้สำเร็จ สิ่งที่เขาได้ไปคือเคอร์เนลของ VM ตัวเองเท่านั้น ถ้าอยากออกไปถึงเครื่องจริง ต้องไปหาช่องโหว่ของ hypervisor (QEMU หรือ KVM) มาใช้ต่ออีกทอดหนึ่ง ซึ่งยากกว่ากันเยอะ แนวคิดแบบนี้เรียกว่า defense in depth คือไม่ฝากความปลอดภัยไว้กับการป้องกันชั้นเดียว

### 3.3 สิ่งที่เราทดสอบเจอ (B2)

ผลเต็ม ๆ อยู่ใน `security/README.md` (PR #8) ถ้าสรุปออกมาจะได้แบบนี้

| ดูจากใน pod | runc | Kata | บอกอะไรเรา |
|---|---|---|---|
| เคอร์เนล | `7.0.0-1014-aws` | `6.18.35` | Kata มีเคอร์เนลของตัวเองจริง |
| RAM / CPU | 7776 MB / 2 | 192 MB / 1 | Kata มองไม่เห็นทรัพยากรของเครื่องจริง |
| รุ่นเครื่อง | `m8i.large` | อ่านไม่ได้ | ข้อมูลของเครื่องจริงถูกซ่อนอยู่หลัง VM |
| `/dev/core` | มี (ชี้ไปที่ `/proc/kcore`) | ไม่มี | runc อยู่ติดกับเคอร์เนลเครื่อง |
| `dmesg` | ถูกห้าม | อ่านได้ แต่เป็น log ของ VM | ที่ Kata แตะได้คือเคอร์เนลของตัวเอง ไม่ใช่ของเครื่อง |
| มองจาก worker (`ps`) | เห็น process nginx ตรง ๆ | เห็นแค่ `qemu-system-x86` | process ใน Kata ถูกห่อไว้ใน VM |

ข้อที่เราว่าน่าสนใจที่สุดคือ `dmesg` ตอนแรกที่เห็นว่า Kata อ่านได้แต่ runc โดนห้าม เราคิดว่า Kata หลวมกว่าเสียอีก แต่พอดูข้างในแล้วเป็น log ตอนบูตของ VM เอง ใน runc ต้องห้ามเพราะนั่นคือ log ของเคอร์เนลเครื่องจริง ส่วนใน Kata ไม่มีอะไรของเครื่องจริงอยู่ในนั้นเลย ข้อนี้เลยกลายเป็นหลักฐานอีกชิ้นว่า Kata แยกเคอร์เนลออกมาจริง

### 3.4 ข้อจำกัด

ถึง Kata จะช่วยได้มาก แต่ก็ไม่ได้ทำให้ระบบปลอดภัย 100% ยังมีอีกหลายเรื่องที่ต้องระวัง

- hypervisor เองก็มีช่องโหว่ได้ ถ้า QEMU หรือ KVM มีบั๊ก ก็ยังหลุดออกจาก VM ได้ เคยมีให้เห็นแล้วอย่าง VENOM (CVE-2015-3456) ใน QEMU Kata แค่ทำให้ต้องเจาะสองชั้นแทนชั้นเดียว
- ถ้าตัวแอปมีช่องโหว่ Kata ก็ช่วยไม่ได้ สมมติ nginx ถูกเจาะ คนร้ายก็ยังได้ทุกอย่างที่อยู่ใน pod นั้น รวมถึงอะไรก็ตามที่ pod เข้าถึงได้ทางเครือข่ายหรือผ่าน token ของ Kubernetes
- อะไรที่แชร์จากเครื่องเข้าไปใน VM ยังเป็นช่องทางได้ เช่น volume ที่ mount เข้าไป หรือการรัน pod แบบ `privileged` ซึ่งเป็นเหตุผลที่กติกากลุ่มเราห้ามใช้
- VM ยังใช้ CPU ตัวเดียวกับเครื่อง ช่องโหว่ฝั่ง CPU อย่าง Spectre หรือ Meltdown จึงยังต้องพึ่งการแก้ที่ระดับ CPU และเคอร์เนลอยู่ดี
- ต้องจ่ายด้วยทรัพยากร VM ทุกตัวกิน RAM เพิ่ม (ของเราจองไว้ 160Mi ต่อ pod) และเริ่มทำงานช้ากว่า runc ตัวเลขจริงดูได้จากงาน benchmark ของ pooad (B3)

### 3.5 ควรใช้ Kata ตอนไหน

Kata เหมาะกับงานที่ต้องรันโค้ดที่เราไม่ไว้ใจ หรือมีหลายคนหลายทีมใช้เครื่องร่วมกัน เช่น cluster ของกลุ่มเรา ระบบที่ให้ลูกค้าอัปโหลดโค้ดมารัน หรือ CI ที่ต้องรันโค้ดจาก pull request ของคนนอก แต่ถ้าเป็นงานของเราเองทั้งหมด และอยากได้ความเร็วหรืออยากประหยัด RAM ให้มากที่สุด runc ก็ยังเป็นตัวเลือกที่ดีกว่า

## 4. สรุป

Kata Containers ให้ pod แต่ละตัวมี VM และเคอร์เนลเป็นของตัวเอง ถ้าเคอร์เนลใน pod ไหนถูกเจาะ ก็ยังไม่ได้แปลว่าคนร้ายหลุดถึงเครื่องทันที ผลทดสอบของเราก็ยืนยันแบบนั้น pod Kata มองไม่เห็นเคอร์เนล ทรัพยากร หรือรุ่นของเครื่องจริง และฝั่ง worker เองก็มองไม่เห็น process ที่อยู่ข้างใน pod Kata แต่ของพวกนี้ต้องแลกกับ RAM และเวลาเริ่มที่เพิ่มขึ้น แล้วก็ยังต้องไว้ใจ hypervisor อยู่ดี เลยพูดได้ว่า Kata เพิ่มชั้นกั้นให้ระบบ แต่ไม่ได้ทำให้ปลอดภัย 100%
